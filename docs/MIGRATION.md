# Миграция и импорт старых конфигов

Главный принцип: **старые VPN-конфиги должны продолжать работать.** Новая система
их не удаляет и не пересоздаёт. Она их обнаруживает, импортирует в интерфейс и
показывает источник и уровень управления.

## Модель совместимости

Состояния импортированных записей (см. `ConfigSource` в `@novpn/shared`):
`observed` → `imported` → `unassigned` / `adopted` → `managed`, а также `legacy`
(обслуживается старым стеком). Управление (отключение по лимиту и т.п.)
применяется только к записям, которыми NoVPN реально умеет управлять.

## Порядок импорта (read-only сначала)

1. Read-only аудит сервера агентом.
2. Найти Docker-контейнеры и системные службы.
3. Найти Xray; найти Amnezia/AmneziaWG/WireGuard; найти HTTP/SOCKS proxy.
4. Определить конфигурационные файлы.
5. Определить пользователей, UUID, public keys, proxy login.
6. Сопоставить с БД панели по надёжным идентификаторам
   (UUID / public key / proxy username / internal id / server id / связи из старой БД).
7. Импортировать найденные записи **без изменения** серверной конфигурации.
8. Проверить, что старые подключения продолжают работать.

Если владельца определить нельзя — не угадывать: импортировать как
**«Не назначен»**, админ назначит позже. Имя устройства и ОС не выдумывать.
Если трафик/последняя активность недоступны — показывать **«Мониторинг
недоступен»**, а не ноль.

## Сосуществование стеков

По умолчанию не занимать порты старых сервисов и не переписывать их конфиги.
Варианты после аудита: (1) аккуратно добавлять клиентов к существующему сервису,
если он это безопасно поддерживает; или (2) отдельный управляемый инстанс на
свободном порту, без конфликтов. Старая и новая системы могут временно работать
параллельно. Не менять firewall без проверки текущих правил; не перезапускать
legacy-сервис ради простого импорта.

## Backup основной установки (перед любыми изменениями)

Скрипты: `deploy/scripts/backup.sh`, проверка: `deploy/scripts/verify-backup.sh`.

1. Дамп БД (SQLite: копия файла + `.dump` схемы и данных).
2. Сохранить схему отдельно.
3. Проверить дамп; получить список содержимого; при возможности восстановить
   во временную БД.
4. Backup persistent volumes.
5. Зафиксировать Docker image + digest.
6. Зафиксировать текущий Git commit (сейчас prod = `DanT2000/ZeroVPN@main`).
7. Сохранить конфигурацию Coolify (env-имена, домен, labels, volumes).
8. Вычислить checksum резервных файлов (sha256).

Backup **нельзя**: коммитить в Git, класть в публичную папку сайта, выводить
вместе с секретами, считать проверенным без попытки чтения/восстановления.

## Migration rehearsal (на копии)

1. Восстановить дамп prod во временную БД.
2. Прогнать импорт-адаптер старой схемы (`users/devices/app_settings/vpn_servers`)
   в новую.
3. Проверить: старые коды сохранены, legacy UUID и public keys на месте,
   пользователи не потеряны, устройства сопоставлены.
4. Проверить новую версию на временном адресе / внутреннем endpoint.

## Безопасная замена production

1. Зафиксировать текущее состояние. 2. Backup БД и томов. 3. Сохранить
commit/image. 4. Сохранить конфигурацию приложения и домена.
5. Подготовить production-кандидат отдельно. 6. Проверить миграции на копии.
7. Проверить импорт. 8. Проверить на временном адресе.
9. **Только потом** переключить FQDN `vpn.appswire.ru`.
10. Старую версию не удалять сразу — оставить как rollback.

## Rollback

1. В Coolify вернуть FQDN `vpn.appswire.ru` на прежнее приложение
   (`NoVPN`, `DanT2000/ZeroVPN@main`, сохранённый commit/image).
2. Восстановить БД из проверенного дампа в исходный volume при необходимости.
3. Проверить healthcheck и вход администратора.
4. Зафиксировать инцидент, разобрать причину, повторить rehearsal.

Точные пути дампов, checksum и пошаговый rollback заполняются в момент
реального backup (значения — вне Git).
