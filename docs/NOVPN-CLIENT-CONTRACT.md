# Контракт NoVPN Panel ↔ NoVPN Desktop

Единый документ между панелью (этот репозиторий) и клиентским приложением. Обе стороны
реализуют **только то, что здесь описано**. Поле, известное одному репозиторию, — ошибка
процесса, а не «временное решение».

- **Версия контракта:** `schemaVersion = 1`
- **Владелец разделов 1–7:** панель (backend). **Разделов 8+:** клиент.
- Порядок изменения: правим контракт → правим фикстуры → бэкенд → клиент → contract-тесты → E2E.

---

## 1. Продуктовая модель

**Умная маршрутизация — режим по умолчанию для всех.** Обычный пользователь не выбирает
между техническими режимами и вообще не видит слов «smart» и «full».

**Полный VPN — не пользовательский переключатель.** Его выдаёт администратор панели,
когда это нужно конкретному сценарию. Клиент **никогда не конструирует Full сам** из
Smart-данных: единственный источник истины — то, что выдала панель.

Классический постоянный полный туннель без всей этой механики остаётся отдельным понятным
способом — AmneziaWG. Не смешивать его с Xray Full ни технически, ни в текстах.

Пользовательские термины: «Умная маршрутизация», «Полный VPN», «напрямую / через VPN»,
«резервный канал». Технические (`upstream.json`, `geosite`, `routingMode=full`) — только
в админской части.

---

## 2. Точки входа

Клиент знает **только ссылку-подписку**, выданную его провайдером. Всё остальное он
получает от той же панели, по тому же токену. Панель разработчика ни для чего не
захардкожена: разные провайдеры — разные панели.

| Назначение | Метод и путь | Авторизация |
|---|---|---|
| Метаданные подписки | `GET /sub/<subToken>/meta.json` | sub-токен в пути |
| Агрегированная подписка | `GET /sub/<subToken>/full` | sub-токен в пути |
| Подписка одного сервера | `GET /sub/<subToken>/server/<serverId>/full` | sub-токен в пути |
| Манифест списков | `GET /routing/manifest.json` | публично |
| Списки маршрутизации | `GET /routing/{upstream,sites,apps}.json` | публично |

> **`/api/public/bootstrap` клиенту не подходит.** Он авторизуется cookie-сессией,
> которую заводит вход по `accessToken` — токену личного кабинета. Это **другой токен**,
> у приложения его нет и быть не должно. Без сессии эндпоинт отдаёт анонимный ответ.

Недоступность панели, истёкший доступ или исчерпанный трафик дают `404`. `404` — **не**
повод стереть рабочий кэш: см. раздел 9.

## 3. `GET /sub/<subToken>/meta.json`

```json
{
  "schemaVersion": 1,
  "panel": { "name": "NoVPN", "origin": "https://vpn.appswire.ru" },
  "routingResources": {
    "manifest": "https://vpn.appswire.ru/routing/manifest.json",
    "upstream": "https://vpn.appswire.ru/routing/upstream.json",
    "sites":    "https://vpn.appswire.ru/routing/sites.json",
    "apps":     "https://vpn.appswire.ru/routing/apps.json"
  },
  "servers": [
    {
      "id": "s_pvU-7Nj_",
      "host": "1.vpn.appswire.ru",
      "remark": "🚀 Франция",
      "protocols": ["xray", "amneziawg", "http", "https", "socks5"],
      "online": true,
      "subLink": "https://vpn.appswire.ru/sub/<subToken>/server/s_pvU-7Nj_/full",
      "routing": {
        "mode": "smart",
        "lanAccess": false,
        "fallbackTypes": null,
        "ownExceptions": 7
      }
    }
  ]
}
```

`servers[]` держится **1:1 с агрегированной подпиской** `/sub/<t>/full`: каждому профилю
в приложении соответствует ровно одна запись. Сервер, которого нет в подписке, в
`meta.json` не появляется.

### Ключ сопоставления — `host`

`serverId` внутри конфига подписки **не передаётся**. `remark` совпадает с `remarks` в
конфиге, но администратор переименовывает серверы, и значок (`flagEmoji`) перебивает флаг
страны. Поэтому:

1. основной ключ — **`host`** (домен endpoint'а, уникален);
2. `remark` — только запасной эвристический ключ;
3. `id` — для логов и для `subLink`, из подписки его не извлечь.

Подписка — это **Xray-конфиг** (или массив конфигов, по одному на сервер), а не список
`vless://`-ссылок. Адрес лежит в `outbounds[].settings.vnext[].address`; строки вида
`@host:port` в теле искать бесполезно.

Адрес в исходящем — **буквально тот же** `host`: при сборке подписки endpoint
подменяется на текущий `host:port` сервера, чтобы смена домена или порта доезжала до
подписчиков без перевыпуска конфигов. Порт при этом может отличаться (у endpoint'а бывают
`legacyPorts` — старые порты, оставленные для ранее выданных конфигов), поэтому
**сопоставлять только по хосту, порт игнорировать**. Альтернативных доменов у endpoint'а
не бывает: домен один, меняются только порты.

`remark` формируется как `flagEmoji + ' ' + name`, где `flagEmoji` — свой значок сервера,
а если он не задан — флаг из `country`. Это ровно то, что видно в панели, и ровно то, что
попадает в `remarks` конфига: имя сервера в приложении обязано совпадать с именем в панели.

## 4. `routing.mode` — семантика

`mode` описывает **профиль**, а не конкретные правила движка. Каждый движок применяет его
в своей идиоме — и здесь есть ловушка, которую надо знать обеим сторонам.

> ### ⚠ Направление «smart» в двух движках противоположно
>
> **Конфиг Xray-подписки** (телефоны, Happ): по умолчанию **всё идёт через VPN**, а список
> исключений уходит `direct`. Это whitelist-обход.
>
> **Списки для NoVPN Desktop**: по умолчанию **всё идёт напрямую**, а список перечисляет
> то, чему нужен VPN. Прямо записано в самом `sites.json`: *«По умолчанию весь трафик идёт
> напрямую. Здесь перечислено только то, чему нужен VPN, и отдельно то, что обязано
> остаться напрямую»*. У записей есть поле `route: "vpn" | "direct"`.
>
> Одно слово «smart», две противоположные базы. Не переносить правила одного движка в
> другой механически.

### `smart` (по умолчанию, и при отсутствии поля)

Выборочная маршрутизация. Направление задают **сами списки** (`route` у записи), а не
режим. Дополнительно, независимо от списков:

- приватные подсети — по `lanAccess` (см. раздел 5);
- **BitTorrent** идёт напрямую. В конфиге Xray это отдельное правило (`protocol:
  bittorrent` по результату sniffing). Для движков без матчера протокола отдельного
  правила не требуется: при базе «по умолчанию direct» торрент и так уходит напрямую.

Когда все каналы недоступны, терминальный fallback — **`direct`**: осознанный компромисс,
пользователь остаётся в сети.

### `full`

Весь трафик идёт через VPN, база — «в туннель», списки не применяются. Относительно
`smart` **убираются**:

- правило доменных исключений целиком — **`ownExceptions` в этом режиме не применяются**,
  включая свои домены сервера;
- исключение для BitTorrent (торрент тоже идёт в туннель).

Терминальный fallback становится **`block`** (fail-close). Пользователь явно выбрал
«всё через VPN»; падение в `direct` при потере всех каналов — утечка реального IP
открытым текстом. Клиент обязан повторить это поведение.

### Одинаково в обоих режимах

- **QUIC (UDP/443) блокируется.** Без этого YouTube «зависает»: браузер открыл QUIC, UDP
  по VLESS теряется, отката на TCP не происходит. Блок заставляет браузер сразу перейти
  на HTTP/2 поверх TCP.
- **Анти-петля:** трафик самого VPN-транспорта не заворачивается в туннель.
- `lanAccess` работает одинаково.

## 5. `lanAccess` — обратите внимание на направление

Значение | Приватные подсети идут | Для чего
---|---|---
`false` (по умолчанию) | **напрямую**, мимо туннеля | обычный случай: локалка пользователя остаётся его локалкой
`true` | **через туннель** | самохостер добирается до локальной сети *своего* сервера через VPN

Это легко реализовать наоборот. `true` — это «пустить LAN в туннель», а не «исключить LAN».

---

## 6. `fallbackTypes` — это транспорт, а не маршрутизация

Список прокси-каналов (`https` / `http` / `socks`), разрешённых как **аварийный
транспорт**, если Xray заблокируют. Панель по нему фильтрует прокси-аккаунты пользователя
на этом сервере и добавляет их в конфиг отдельными тирами.

- `null` — разрешены все доступные;
- `[]` — аварийных каналов нет.

**Списком исключений маршрутизации это не является.** Использовать его для `direct` нельзя.

## 7. Списки маршрутизации и их версии

`/routing/{upstream,sites,apps}.json` — стабильные адреса, менять их можно только
согласованной с клиентом миграцией.

- `upstream.json` — `{"items": [...]}`. Панель собирает его из нескольких источников
  (AutoRoute: приоритеты, конфликты, версии, откат), но **формат для клиента неизменен**.
- `sites.json`, `apps.json` — управляемые файлы панели.

### Условный GET

Каждый файл отдаётся с сильным `ETag` (sha256 содержимого) и `Last-Modified`. Клиент
обязан присылать `If-None-Match` (или `If-Modified-Since`) и корректно обрабатывать `304`,
не перекачивая неизменившийся список.

### `GET /routing/manifest.json`

```json
{
  "schemaVersion": 1,
  "files": [
    { "name": "upstream", "version": 12, "sha256": "…", "bytes": 24245,
      "updatedAt": "2026-08-27T12:17:58.022Z", "url": "https://…/routing/upstream.json" }
  ]
}
```

Один запрос, чтобы понять, что изменилось, вместо трёх условных GET'ов. `sha256` — по
содержимому; `version` растёт и при правках форматирования, поэтому сравнивать надо хеш.

## 8. Совместимость и деградация

- **Нет `routing` или нет `mode`** → `smart`. Старые подписки не ломаются.
- **Нет `meta.json`** (старая панель или чужой провайдер) → `smart`, Full не предлагается.
- **Незнакомые поля** клиент игнорирует, не падая.
- **`schemaVersion.major` выше поддерживаемого** → безопасная деградация в `smart` +
  сообщение о необходимости обновиться.

### Зарезервировано, панелью пока не заполняется

`expiresAt?`, `fallbackProfileId?` — на будущее (временная выдача Full администратором).
Клиент должен уметь их прочитать, но не рассчитывать на их наличие. Никакого хардкода
«Full всегда 12 часов».

### Отзыв Full

Full — ограниченная capability, выданная бэкендом. Локальный флаг (`localStorage`,
настройка приложения) её источником быть не может.

Если на рефреше выбранный сервер стал `smart` или исчез — клиент переходит на Smart
(на `fallbackProfileId`, если задан, иначе на доступный smart-сервер). Предпочтителен
бесшовный переход; зависшую full-сессию оставлять нельзя.

## 9. Разделы клиента

Владелец — репозиторий клиентского приложения. Заполняется его стороной:

- **9.1 Refresh.** Когда дёргается `meta.json`, когда конфиг подписки, когда списки.
- **9.2 Кэш и недоступность панели.** Подключение по last-known-good; один таймаут не
  стирает рабочий кэш.
- **9.3 Сопоставление серверов.** Матчинг подписки с `meta.json` по `host`.
- **9.4 Поведение при отзыве Full.**
- **9.5 Локальные правила пользователя.** Список сайтов, который пользователь ведёт сам
  (в т.ч. одним кликом из браузерного расширения), хранится локально и с панелью не
  синхронизируется.

## 10. Фикстуры и contract-тесты

Канонические фикстуры лежат в этом репозитории и используются **обеими** сторонами:

- `smart-only` — один сервер, `mode: smart`;
- `full` — сервер с `mode: full`;
- `smart+full` — оба;
- `legacy` — ответ без блока `routing` (обязан читаться как smart);
- `expired-full` — `expiresAt` в прошлом;
- `invalid-routing-version` — `schemaVersion.major` выше поддерживаемого.

Тесты обязаны проверять: ответ соответствует схеме; `mode` — только из допустимого
множества; smart содержит ссылки на все routing-ресурсы; full не требует smart-only
ресурсов; отсутствие `routing` читается как smart.
