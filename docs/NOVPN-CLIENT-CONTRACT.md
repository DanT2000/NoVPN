# Контракт NoVPN Panel ↔ NoVPN Desktop

Единый документ между панелью (этот репозиторий) и клиентским приложением. Обе стороны
реализуют **только то, что здесь описано**. Поле, известное одному репозиторию, — ошибка
процесса, а не «временное решение».

- **Версия контракта:** `schemaVersion = 1`
- **Владелец разделов 1–8:** панель (backend). **Раздела 9:** клиент.
- Порядок изменения: правим контракт → правим фикстуры → бэкенд → клиент → contract-тесты → E2E.

---

## 1. Продуктовая модель

**Умная маршрутизация — режим по умолчанию для всех.** Что не работает в России — идёт
через VPN, всё остальное напрямую. Список («что не работает») собирает панель в
разделе **AutoRoute** из нескольких источников; клиент его скачивает и исполняет.

**Полный VPN — второй профиль того же сервера**, весь трафик в туннель без исключений.
Он есть у **всех** пользователей сервера, на котором включена умная маршрутизация; если
администратор её выключил, сервер отдаёт только полный профиль. Пер-пользовательских
запретов нет намеренно: на сервере ничего не блокируется, а лишний трафик — лимиты самого
человека. Клиент **никогда не конструирует Full сам** — только показывает профиль, который
пришёл.

Классический постоянный туннель без всей этой механики остаётся отдельным понятным
способом — AmneziaWG. Не смешивать его с Xray Full ни технически, ни в текстах.

Пользовательские термины: «Умная маршрутизация», «Полный VPN», «напрямую / через VPN»,
«резервный канал». Технические (`upstream.json`, `geosite`, `profileId`) — только в
админской части.

## 2. Точки входа

Клиент знает **только ссылку-подписку**, выданную его провайдером. Всё остальное он
получает от той же панели, по тому же токену. Панель разработчика ни для чего не
захардкожена: разные провайдеры — разные панели.

| Назначение | Метод и путь | Авторизация |
|---|---|---|
| Метаданные подписки | `GET /sub/<subToken>/meta.json` | sub-токен в пути |
| Агрегированная подписка (все профили) | `GET /sub/<subToken>/full` | sub-токен в пути |
| Один профиль сервера | `GET /sub/<subToken>/server/<serverId>/full[?profile=full]` | sub-токен в пути |
| Манифест списков | `GET /routing/manifest.json` | публично |
| Список AutoRoute (JSON) | `GET /routing/upstream.json` | публично |
| Список AutoRoute (DAT) | `GET /routing/autoroute/geosite.dat`, `/routing/autoroute/geoip.dat` | публично |
| Каталог приложений | `GET /routing/apps.json` | публично |

> **`/api/public/bootstrap` клиенту не подходит.** Он авторизуется cookie-сессией,
> которую заводит вход по `accessToken` — токену личного кабинета. Это **другой токен**,
> у приложения его нет и быть не должно.

> **`/routing/sites.json` удалён.** Список сайтов — локальная настройка пользователя
> (раздел 9.5). Клиент при `404` живёт своим локальным списком.

### Отрицательные ответы: «панель не ответила» ≠ «доступ отозван»

Клиент держит last-known-good и по сетевой ошибке кэш не стирает. Чтобы отзыв доступа
при этом реально срабатывал, `meta.json` разделяет два случая:

| Ситуация | Ответ | Что делает клиент |
|---|---|---|
| Панель недоступна: таймаут, DNS, обрыв, `5xx` | — | работает по кэшу, кэш **не трогает** |
| Токен неизвестен | `404` `{"error":{"type":"not_found"}}` | авторитетно: профили больше не предлагать |
| Доступ отключён администратором | `403` `{"error":{"type":"disabled"}}` | то же + показать причину |
| Срок доступа истёк | `403` `{"error":{"type":"expired"}}` | то же |
| Лимит трафика исчерпан | `403` `{"error":{"type":"traffic"}}` | то же |

Правило простое: **любой ответ 4xx — это ответ панели, то есть авторитетный сигнал.**
Отсутствие ответа — не сигнал.

## 3. `GET /sub/<subToken>/meta.json`

```json
{
  "schemaVersion": 1,
  "panel": { "name": "NoVPN", "origin": "https://vpn.appswire.ru" },
  "routingResources": {
    "manifest": "https://vpn.appswire.ru/routing/manifest.json",
    "upstream": "https://vpn.appswire.ru/routing/upstream.json",
    "apps":     "https://vpn.appswire.ru/routing/apps.json",
    "geosite":  "https://vpn.appswire.ru/routing/autoroute/geosite.dat",
    "geoip":    "https://vpn.appswire.ru/routing/autoroute/geoip.dat"
  },
  "profiles": [
    {
      "profileId": "s_pvU-7Nj_",
      "serverId": "s_pvU-7Nj_",
      "host": "1.vpn.appswire.ru",
      "remark": "🇫🇷🚀 Франция",
      "recommended": true,
      "protocols": ["xray", "amneziawg", "http", "https", "socks5"],
      "online": true,
      "subLink": "https://vpn.appswire.ru/sub/<subToken>/server/s_pvU-7Nj_/full",
      "routing": { "mode": "smart", "lanAccess": false, "fallbackTypes": null, "ownExceptions": 0 }
    },
    {
      "profileId": "s_pvU-7Nj_:full",
      "serverId": "s_pvU-7Nj_",
      "host": "1.vpn.appswire.ru",
      "remark": "🇫🇷🚀 Франция · Полный VPN",
      "recommended": false,
      "protocols": ["xray", "amneziawg", "http", "https", "socks5"],
      "online": true,
      "subLink": "https://vpn.appswire.ru/sub/<subToken>/server/s_pvU-7Nj_/full?profile=full",
      "routing": { "mode": "full", "lanAccess": false, "fallbackTypes": null, "ownExceptions": 0 }
    }
  ]
}
```

### Профили, а не серверы

На одном сервере может быть **два профиля** — умный и полный — с одним и тем же `host`.
Поэтому единица контракта — **профиль**:

- `profiles[]` идёт **1:1 и в том же порядке** с конфигами агрегированной подписки
  `/sub/<t>/full` (там массив Xray-конфигов, по одному на профиль);
- умный профиль сервера всегда первый и `recommended: true`; полный — вторым, с
  `remark = "<умный remark> · Полный VPN"`. Сервер с выключенной умной маршрутизацией
  даёт один профиль — полный;
- `profileId` = `<serverId>` для умного, `<serverId>:full` для полного.

### Ключ сопоставления — `profileId`, запасной — `host`

В каждый Xray-конфиг подписки панель кладёт:

```json
"meta": {
  "serverDescription": "🇫🇷🚀 Франция",
  "novpn": { "profileId": "s_pvU-7Nj_", "serverId": "s_pvU-7Nj_", "host": "1.vpn.appswire.ru", "mode": "smart" }
}
```

Xray-core незнакомые поля игнорирует; Happ читает `meta.serverDescription` как раньше.

1. есть `meta.novpn.profileId` → матчим по нему;
2. нет (старая панель) → матчим по адресу из `outbounds[].settings.vnext[].address` ↔
   `profiles[].host`, порт игнорируем, режим `smart`;
3. чужие форматы (Clash YAML, голые vless-ссылки других провайдеров) — `meta.novpn` нет,
   Full там не появляется никогда.

`remark` = флаг страны + значок сервера + имя — ровно то, что в панели и в `remarks`
конфига. Администратор переименовывает серверы, поэтому ключом `remark` быть не может.

## 4. `routing.mode` — семантика

**Базы в обоих движках теперь одинаковые: по умолчанию напрямую.** Список перечисляет то,
чему нужен VPN.

### `smart` (по умолчанию, и при отсутствии поля)

- домены и подсети из AutoRoute (`upstream.json` / DAT) → **в VPN**;
- всё остальное → напрямую;
- приватные подсети — по `lanAccess` (раздел 5);
- BitTorrent: отдельного правила не нужно — при базе «напрямую» он и так идёт мимо VPN;
- когда все каналы недоступны, терминальный fallback — **`direct`**: пользователь остаётся
  в сети.

Панель также умеет унаследованный режим «обход белых списков» (список → напрямую,
остальное в VPN) — он включается администратором на сервере и на проводе выглядит так же
(`mode: smart`), направление уже зашито в правила конфига. Клиент по `mode` его не
отличает и не должен: для десктопа список всегда означает «в VPN».

### `full`

Весь трафик через VPN. Доменных правил нет вовсе — **`ownExceptions` не применяются**,
торрент тоже в туннель. Терминальный fallback — **`block`** (fail-close): падение в
`direct` при потере всех каналов было бы утечкой реального IP. Эквивалент в mihomo:
`MATCH,<vpn-group>` без DIRECT в цепочке.

### Одинаково в обоих режимах

- **QUIC (UDP/443) блокируется** — иначе YouTube «зависает» на потерянном UDP.
- **Анти-петля:** трафик самого VPN-транспорта не заворачивается в туннель.
- `lanAccess` работает одинаково.

---

## 5. `lanAccess` — обратите внимание на направление

Значение | Приватные подсети идут | Для чего
---|---|---
`false` (по умолчанию) | **напрямую**, мимо туннеля | обычный случай
`true` | **через туннель** | самохостер добирается до LAN *своего* сервера через VPN

`true` — это «пустить LAN в туннель», а не «исключить LAN».

---

## 6. `fallbackTypes` — это транспорт, а не маршрутизация

Список прокси-каналов (`https` / `http` / `socks`), разрешённых как **аварийный
транспорт**, если Xray заблокируют. `null` — все доступные; `[]` — аварийных каналов нет.
Списком исключений маршрутизации это не является.

## 7. Списки маршрутизации и их версии

Один датасет AutoRoute — три сериализации:

| Ресурс | Формат | Для кого |
|---|---|---|
| `upstream.json` | `{"items": [...]}` | NoVPN Desktop (MVP) |
| `geosite.dat` | V2Ray/Xray protobuf, тег `NOVPN` (домены) | Xray, sing-box, mihomo geodata, чужие панели |
| `geoip.dat` | V2Ray/Xray protobuf, тег `NOVPN` (подсети) | то же |

### Грамматика `upstream.items[]`

| Элемент | Значение | mihomo |
|---|---|---|
| `example.com` | домен и все поддомены | `DOMAIN-SUFFIX` |
| `full:example.com` | только точное совпадение | `DOMAIN` |
| `keyword:слово` | подстрока в хосте | `DOMAIN-KEYWORD` |
| `regexp:^ad\..*` | регулярка (как в источнике; на практике Go RE2 — компилировать в try, невалидную пропускать) | `DOMAIN-REGEX` |
| `1.2.3.0/24`, `1.2.3.4`, IPv6-CIDR | адрес/подсеть голым | `IP-CIDR` (`/32`, `/128` для голых) |

Всё в нижнем регистре, без дубликатов. Всё в списке — «в VPN». IP-элементы — для того, что
достижимо по адресу без SNI (DC Telegram, CDN): обычный `IP-CIDR` по реальному dst.

В `upstream.json` — **полный** датасет. В телефонный Xray-конфиг панель зашивает
первые по приоритету источников до потолка (сейчас 30 000) — десктопа это не касается.

### Условный GET и манифест

Каждый файл (и DAT тоже) отдаётся с сильным `ETag` (sha256 содержимого) и
`Last-Modified`. Клиент обязан присылать `If-None-Match` и обрабатывать `304`.

`GET /routing/manifest.json`:

```json
{ "schemaVersion": 1, "files": [
  { "name": "upstream", "version": 12, "sha256": "…", "bytes": 24245, "updatedAt": "…", "url": "…/routing/upstream.json" },
  { "name": "apps",     "version": 2,  "sha256": "…", "bytes": 7632,  "updatedAt": "…", "url": "…/routing/apps.json" },
  { "name": "geosite",  "version": 12, "sha256": "…", "bytes": 61230, "updatedAt": "…", "url": "…/routing/autoroute/geosite.dat" },
  { "name": "geoip",    "version": 12, "sha256": "…", "bytes": 1180,  "updatedAt": "…", "url": "…/routing/autoroute/geoip.dat" }
] }
```

Сравнивать надо `sha256`: `version` растёт и при правках форматирования.

## 8. Совместимость и деградация

- **Нет `routing` или `mode`** → `smart`.
- **Нет `meta.json`** (старая панель / чужой провайдер) → `smart`, Full не предлагается.
- **Незнакомые поля** игнорируются.
- **`schemaVersion` выше поддерживаемого** → деградация в `smart` + просьба обновиться.

### Зарезервировано, панелью пока не заполняется

`expiresAt?`, `fallbackProfileId?` — на будущее (временная выдача Full). Никакого
хардкода «Full всегда 12 часов».

### Отзыв Full

Источник истины — только `meta.json`/подписка. Локальный флаг Full источником быть не
может. Если на рефреше выбранный профиль стал `smart` или исчез — переход на Smart
(`fallbackProfileId`, если задан; иначе умный профиль того же сервера; иначе любой умный).
Бесшовно; зависшую full-сессию не оставлять.

## 9. Разделы клиента

Владелец — репозиторий клиентского приложения.

### 9.1 Refresh

- `meta.json` — при старте приложения и перед каждым подключением; даёт профили и их
  `routing.mode`. Кэшируется.
- Конфиг подписки (`/sub/<t>/full`) — при старте (восстановление профилей) и по действию
  пользователя («Обновить» / «Изменить подписку»); при connect берётся актуальный кэш.
- Списки — сначала `manifest.json` (один запрос), сравнение `sha256` с локальными;
  изменившиеся докачиваются условным GET (`If-None-Match`), `304` → локальная копия
  остаётся. Применение атомарное (temp→rename) + валидация; при ошибке — last-known-good.
- Порядок при connect: `meta.json` (режим) → конфиг профиля → списки (если устарели) →
  сборка конфига движка → запуск → DNS/TUN/правила. Всё одной кнопкой, без ручных шагов.

### 9.2 Кэш и недоступность панели

- Клиент хранит last-known-good: `meta.json`, конфиг подписки, списки + их `sha256`.
- **Панель не ответила** (таймаут, DNS, обрыв, `5xx`) и кэш валиден — подключение по кэшу
  разрешено, кэш не трогаем. Один таймаут кэш не стирает.
- **Панель ответила `4xx`** — авторитетный сигнал (таблица в разделе 2): подключение
  блокируется, активная сессия гасится, человеку показывается причина:

  | `type` | Текст пользователю |
  |---|---|
  | `not_found` | «Подписка недействительна» (проверить ссылку) |
  | `disabled` | «Доступ отключён» |
  | `expired` | «Срок доступа истёк» |
  | `traffic` | «Лимит трафика исчерпан» |

  Кэш при этом стирать не обязательно — доступ могут вернуть, — но подключение остаётся
  заблокированным, пока не придёт валидный `200`.
- Нет `meta.json`, но подписка и списки в кэше есть → подключаемся по кэшированному режиму
  (или `smart`, если режима в кэше нет).
- Кэш обновляется только успешным ответом.

### 9.3 Сопоставление профилей

- Профили — из парсинга подписки; ключ `meta.novpn.profileId`, запасной — `host` из
  `outbounds[].settings.vnext[].address` (порт игнорируется).
- Имя для карточки — `meta.remark` как есть (совпадает с панелью).
- Конфиг без записи в `meta` → `smart`. Запись в `meta` без конфига в подписке
  игнорируется: источник профилей — подписка.

### 9.4 Поведение при отзыве Full

- Источник режима — только `meta.json`; локального флага Full нет.
- На рефреше: выбранный профиль стал `smart` или исчез → переход на Smart
  (`fallbackProfileId`, если задан и присутствует; иначе умный профиль того же сервера;
  иначе любой доступный умный). Переподключение бесшовное; зависшую full-сессию не оставляем.
- `expiresAt` (если панель заполнит) → тот же переход по истечении. Хардкода нет.

### 9.5 Локальные правила пользователя

- Пользователь ведёт свой список сайтов (через VPN / напрямую), в т.ч. одним кликом из
  браузерного расширения. Хранится **локально**, с панелью не синхронизируется.
- Накладываются **поверх** списков панели: явный выбор пользователя сильнее готовых списков.
- В режиме `full` локальные доменные правила «напрямую» **не применяются** — иначе была бы
  утечка вопреки fail-close. Правила «через VPN» в `full` избыточны: всё и так в туннель.

## 10. Фикстуры и contract-тесты

Канонические фикстуры лежат в `apps/manager/test/fixtures/contract/` и **генерируются
contract-тестами из настоящих HTTP-ответов** поднятого приложения — разъехаться с
реализацией они не могут. Используются обеими сторонами:

`smart-only`, `full-only`, `smart-and-full`, `legacy-no-routing`, `expired-full`,
`invalid-routing-version`, `upstream`, `routing-manifest`.

Тесты панели проверяют: конверт по схеме; профили 1:1 с конфигами подписки и
`meta.novpn.profileId` в каждом; умный первым и `recommended`; в full нет доменных правил
и терминальное правило в туннель; в smart список → VPN, терминальное → direct; умная
выключена на сервере → только полный профиль, включена → оба у любого пользователя;
DAT — настоящий protobuf с тем же
набором; sha256 манифеста сходится с телом; `304` по `If-None-Match`; `sites.json` → 404;
отзыв доступа → `403` с `type`.
