# NoVPN Desktop — Smart/Full маршрутизация по контракту с Panel

**Дата:** 2026-08-28
**Статус:** дизайн утверждён владельцем, готов к плану реализации
**Контракт (источник истины):** `NoVPN/docs/NOVPN-CLIENT-CONTRACT.md` (schemaVersion 1),
согласован с backend-сессией, живёт на проде, покрыт 12 contract-тестами (сюита 140/140).

> **Δ v2 (2026-08-28, уточнение владельца — backend обновляет контракт/эндпоинты, план ждёт его коммита в прод):**
> - `meta.servers[]` → **`meta.profiles[]`**; на одном сервере может быть ДВА профиля (умный + «Полный VPN», общий `host`, разные `profileId`).
> - **Матчинг — по `profileId`** (из `meta.novpn = {profileId,serverId,host,mode}` в каждом конфиге подписки), `host` — только fallback → `smart`. `profileId` = `<serverId>` / `<serverId>:full`.
> - Smart в Xray-подписке теперь тоже **base-DIRECT** — совпадает с моделью десктопа; ловушка «две противоположные базы» снята.
> - **`sites.json` убран окончательно** — сайты чисто локальные (см. 5.5); серверные списки = `upstream` + `apps`.
> - Новые ресурсы **`geosite.dat` / `geoip.dat`** (V2Ray/Xray DAT, тег `novpn`) в `routingResources`/манифесте; `upstream.json` остаётся — в MVP берём JSON, DAT (mihomo geodata-mode) — опция на будущее.
> - Full — **пер-пользовательский** (клиент-прозрачно: просто видит готовые профили). Владелец требует **совместный E2E до финального «ок»**.
>
> Разделы ниже сверю с финальным коммитом контракта на реальном ответе `meta.json` (profiles) и манифесте; правки будут точечными (профили/profileId, sites→local, geosite/geoip).

## 1. Продукт

- **Smart (умная маршрутизация) — режим по умолчанию для всех.** Обычный пользователь
  не видит слов «smart/full» и **не выбирает** режим. Свободного тумблера Smart/Full нет.
- **Full (полный VPN) — не пользовательская настройка.** Его выдаёт Panel как сервер с
  `routing.mode = "full"`. Клиент **никогда не конструирует Full сам** из Smart-данных.
- Постоянный полный туннель без этой механики — отдельный сценарий (AmneziaWG), не
  смешивать.

Это переносит текущий свободный «выкл. умную = весь трафик в VPN» в разряд серверной
capability. Осознанное изменение поведения, согласовано.

---

## 2. Что даёт контракт (только то, на что опирается клиент)

- **`GET /sub/<subToken>/meta.json`** (тот же токен, что уже есть у клиента): `panel`,
  `routingResources{manifest,upstream,sites,apps}`, `servers[]` с
  `{id, host, remark, protocols, online, subLink, routing{mode, lanAccess, fallbackTypes, ownExceptions}}`.
- **Матчинг сервера — по `host`** (адрес из `outbounds[].settings.vnext[].address` в
  подписке; порт игнорируется; `remark` — только запасной ключ и имя для карточки).
- **`routing.mode ∈ {smart, full}`**, отсутствие поля/блока → `smart`.
- **Списки** `/routing/{upstream,sites,apps}.json` + **`/routing/manifest.json`**
  (`files[]{name,version,sha256,bytes,updatedAt,url}`), условный GET с сильным `ETag`
  (= sha256) и `Last-Modified`, `If-None-Match` → `304` без тела.
- **Отрицательные ответы:** нет ответа (таймаут/сеть/5xx) → панель недоступна; **любой
  4xx — авторитетный ответ панели** (`404 not_found`, `403 disabled|expired|traffic`).
- Зарезервировано, панель пока не заполняет: `expiresAt?`, `fallbackProfileId?`.

Наблюдение: у **десктопа база маршрутизации = DIRECT** (списки перечисляют, чему нужен
VPN), у Xray-подписки телефонов — наоборот. Направление задают записи (`route`), не режим.
Существующая клиентская модель уже правильная — движок не переписываем, только надстраиваем.

---

## 3. Архитектура (адаптер vs движок)

Разделяем два слоя (уже частично так, доводим до чистого разделения):

- **Адаптер NoVPN** (backend-facing): подписка, `meta.json`, списки, профили, режим,
  кэш, здоровье. Знает про Panel и контракт. Не знает про TUN/mihomo.
- **Движок** (engine): mihomo, TUN, DNS, жизненный цикл процесса, применение маршрутов.
  Знает про mihomo-конфиг. Не знает про Panel.

Между ними — `Profile` (выбранный сервер + его `routing.mode` + policy) и `RuleSet`
(итоговые правила). Не смешивать в god-object.

---

## 4. Поток «Подключиться» (одна кнопка делает всё)

```
Connect:
  1. meta.json (свежий или валидный кэш) → серверы + режим выбранного (по host)
       ├─ 4xx → блок подключения + причина (type), сессию гасим            [см. §7]
       └─ нет ответа + валидный кэш → идём по last-known-good
  2. конфиг подписки выбранного сервера (кэш/сеть)
  3. списки: manifest.json → сравнить sha256 → докачать изменившееся (If-None-Match/304)
       атомарно (temp→rename) + валидация; ошибка → last-known-good
  4. собрать mihomo-конфиг по mode (smart|full) + lanAccess + user rules
  5. запустить движок → DNS → TUN/прокси → применить правила → health-check
```

Никаких ручных «скачать правила / обновить DAT / перезапустить». Ошибка на любом шаге —
понятный статус, откат на last-known-good, не битое состояние.

## 5. Компоненты и изменения

### 5.1 Адаптер: `meta.json` (новый модуль `meta.rs` + мостик)
- Fetch `GET {base}/sub/<subToken>/meta.json` (base/токен — из сохранённой подписки, как
  сейчас для `lists.rs::base_of`). Кэш в `%APPDATA%\NoVPN\meta.json` (last-known-good).
- Парсинг в `Meta { schema_version, panel, routing_resources, servers[] }`,
  `ServerMeta { host, remark, online, routing: RouteMeta { mode, lan_access, .. } }`.
- Деградация: нет `meta` / чужой провайдер / незнакомый major → `smart`, Full не предлагается.
- Отдаёт фронту режим по каждому серверу + причину при 4xx.

### 5.2 Матчинг профилей по `profileId` (host — fallback)
- Профили — из парсинга агрегированной `/sub/<t>/full` (`sub.rs`), **по одному конфигу на
  профиль**; сервер с обоими режимами даёт два конфига (умный, затем `:full`).
- Из каждого конфига берём `meta.novpn.profileId` (+ serverId, host, mode). Сопоставление
  `config.meta.novpn.profileId ↔ meta.profiles[].profileId` → `mode`, `lanAccess`, `remark`
  (имя), `recommended`.
- Нет `meta.novpn` (старая панель / чужой формат Clash/ссылок) → fallback по **host**
  (`outbounds[].settings.vnext[].address`, без порта), режим `smart`, Full не появляется.
- Ключ именно `profileId`, а не `host`: у умного и полного профилей одного сервера host общий.

### 5.3 `lists.rs`: manifest + условный GET + грамматика upstream + last-known-good
- Серверные списки теперь **`upstream` + `apps`** (`sites` убран; сайты — локальные, см. 5.5).
- Сначала `GET routingResources.manifest`; сравнить `files[].sha256` с локальными; качать
  только изменившиеся условным GET (`If-None-Match`); `304` → локальная копия. (Fallback без
  manifest: прямой условный GET файлов.)
- **Грамматика `upstream.items[]`** (смешанные домены и IP, всё → VPN в smart) → mihomo:
  - `example.com` → `DOMAIN-SUFFIX`; `full:x` → `DOMAIN`; `keyword:x` → `DOMAIN-KEYWORD`;
    `regexp:x` → `DOMAIN-REGEX`; `1.2.3.0/24` / `1.2.3.4`(→/32) / IPv6(-CIDR) → `IP-CIDR`.
  - `regexp:` — компиляцию каждого **в try, невалидные пропускать и логировать** (регэкспы
    из чужих источников, панель их не валидирует; на практике Go RE2).
  - IP-виды под fake-ip DNS матчат только прямые соединения по реальному dst-IP (Telegram DC,
    CDN без SNI) — обычный `IP-CIDR`, без no-resolve-плясок; это и есть их назначение.
  - Текущий `absorb` трактует всё как голый суффикс — доделать под грамматику.
- geosite.dat/geoip.dat (тег `novpn`) = тот же датасет в DAT; опция через mihomo geodata-mode,
  в MVP не тащим (JSON `upstream` покрывает и домены, и IP).
- Хранить рядом `sha256`/`ETag`/`version` (статус «Правила vN»). Атомарно (temp→rename) +
  валидация. Любая ошибка → last-known-good, рабочие файлы не стираем.

### 5.4 `core.rs`: режимы в движке
- **smart** — текущая выборочная сборка (`build_rules`): подсети/локалка, user_domains,
  списки (`route`), процессы, `MATCH,DIRECT`. Без изменений по сути.
- **full** — новая ветка: `MATCH,<vpn-group>` (всё в туннель), **без доменных исключений**
  (`ownExceptions` не применяем), **fail-close** (в группе нет `DIRECT`-фолбэка: мёртвый
  прокси = обрыв, не утечка), bittorrent в туннель (отдельного правила не нужно).
- **Одинаково в обоих режимах:** блок **QUIC** (`REJECT` для udp/443), **анти-петля**
  (VPN-транспорт мимо туннеля — на уровне outbound/DIRECT для host сервера),
  **`lanAccess`**: `false` → приватные подсети `DIRECT` (текущее `push_subnets`),
  `true` → LAN в туннель (эти правила убрать). `lanAccess` — из `meta`, серверная политика.
- Терминальный fallback smart = `MATCH,DIRECT` (как сейчас), full = fail-close.

> Реконсиляция для плана: текущая пользовательская настройка «Локальная сеть — напрямую»
> (`bypass_local`) пересекается с серверным `lanAccess`. Решение: `lanAccess` из `meta`
> задаёт направление приватных подсетей; пользовательские «свои локальные домены»
> остаются как удобство. Точное поведение при конфликте — зафиксировать в плане.

### 5.5 `store.tsx`: проводка режима, отзыв, fallback
- Убрать `smartRouting` как свободный тумблер; режим берётся из `meta` по выбранному серверу.
- На рефреше/reconnect: если сервер стал `smart`/исчез → бесшовный fallback на Smart
  (`fallbackProfileId` если задан → доступный smart-сервер → тот же сервер как smart).
- 4xx от `meta`: заблокировать подключение, показать причину, погасить активную сессию.
- Локальные правила пользователя (`browser-rules.json` + состояние) — поверх списков; в
  `full` доменные «напрямую» игнорируются (fail-close), «через VPN» избыточны.

### 5.6 UI
- **Убрать** тумблер «Умная маршрутизация» (Home + Settings).
- **Селектор серверов**: у каждого сервера бейдж режима — smart «Умная маршрутизация ·
  Рекомендуется», full «Полный VPN · Для особых случаев». Имя = `meta.remark`.
- **Статус**: «Сервер · Режим · Правила vN · Обновлено N мин». Full → «Режим: Полный VPN».
  Технические детали — по раскрытию.
- **Full нигде нет** → вторичная ссылка «Нужен полный VPN?» с текстом: доступен только если
  предоставил провайдер; для постоянного полного VPN — AmneziaWG. Без нерабочего свитча.
- **Причины 4xx** — понятные плашки: «Подписка недействительна» / «Доступ отключён» /
  «Срок доступа истёк» / «Лимит трафика исчерпан».
- **Диагностика**: кнопка «Проверить маршрутизацию» — движок, TUN, DNS, routing-файлы,
  выбранный профиль, доступность панели, публичный маршрут; понятный итог, technical dump
  копируется отдельно.

## 6. Совместимость

- Нет `meta.json` (старая панель / **чужой провайдер** — приложение принимает подписку
  любого) → `smart`, Full не предлагается. Ничего не ломается.
- Нет `routing`/`mode` → `smart`. Незнакомые поля игнорируем. `schemaVersion.major` выше
  поддерживаемого → безопасная деградация в `smart` + «нужно обновиться».
- Существующие подписки и списки продолжают работать.

---

## 7. Ошибки и устойчивость

| Ситуация | Клиент |
|---|---|
| Нет ответа (таймаут/сеть/5xx) | панель недоступна → подключение по last-known-good, кэш не трогаем |
| `404 not_found` | «Подписка недействительна» — блок, причину показать |
| `403 disabled/expired/traffic` | «Доступ отключён/Срок истёк/Лимит исчерпан» — блок, причину показать, активную сессию погасить |
| Full отозван (сервер стал smart/исчез) | бесшовный fallback на Smart |
| Ошибка списков | last-known-good |

Кэш при 4xx не обязательно стирать (доступ могут вернуть), но подключение блокируется до
валидного `200`.

## 8. Тестирование

- **Фикстуры** — канонические из backend `apps/manager/test/fixtures/contract/`
  (`smart-only`, `full`, `smart+full`, `legacy`, `expired-full`, `invalid-routing-version`,
  `routing-manifest`), забираем как эталон — не расходятся с реализацией панели.
- **Client contract-тесты**: разбор `meta.json` (все режимы, legacy, unknown major),
  матчинг по host, manifest/ETag/304, сборка mihomo-конфига для smart и full (fail-close,
  QUIC-блок, lanAccess прямой/инвертированный), обработка 4xx по каждому `type`,
  fallback при отзыве Full, last-known-good при недоступности.
- **E2E с backend** (тестовый пользователь на боевой панели): smart, full, отзыв Full на
  живую (backend меняет режим сервера → клиент переключается без разрыва), обновление
  списков без переустановки (реальная смена sha256 upstream → атомарный temp→rename).

## 9. Вне объёма / на будущее

- Per-user выдача Full и `expiresAt`/`fallbackProfileId` — панель пока не заполняет; клиент
  умеет прочитать, но не рассчитывает. Никакого хардкода «12 часов».
- Два профиля (smart+full) на одном сервере — если backend введёт, предупредит заранее.
- Firefox-расширение и прочее вне маршрутизации — отдельные задачи.

## 10. Риски

- **Реконсиляция `lanAccess` ↔ пользовательская локальная настройка** — уточнить в плане.
- **Извлечение host** из разных форматов подписки (Xray-JSON/Clash/ссылки) — покрыть тестами.
- **fail-close/QUIC в mihomo** — проверить на реальном движке (mihomo `REJECT`, отсутствие
  DIRECT-фолбэка в группе) в E2E.
- **meta.json — новый сетевой шаг перед connect** — не должен ломать оффлайн-подключение по
  кэшу; строго last-known-good.
